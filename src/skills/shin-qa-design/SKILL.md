# Multi Agent QA Design Workflow

QA 観点からテスト戦略を総合的に設計するワークフロー。

**前提: planner-workflow で作成された計画書を入力として受け取る。**

## 全体フロー

```
┌─────────────────────┐
│  planner-workflow   │
│  (計画書を出力)      │
└──────────┬──────────┘
           │ 計画書ファイル
           ▼
┌─────────────────────┐
│  qa-design-workflow │ ← 今ここ
│  (テスト設計書出力)   │
└──────────┬──────────┘
           │ テスト設計書ファイル
           ▼
┌─────────────────────┐
│  execute-workflow   │
│  (テスト+実装+検証)  │
└─────────────────────┘
```

## 入力

**計画書ファイルパス（必須）:**
```bash
/shin-qa-design ./docs/{topic}/plan.md
```

## Workflow

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Plan Reader │ ──▶ │  Analyzer   │ ──▶ │  Designer   │ ──▶ │   Review    │
│ (計画読込)   │     │ (リスク分析) │     │ (テスト設計) │     │ (外部レビュー) │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
                                                                   │
                                                                   ▼
                                                          ┌─────────────────┐
                                                          │ テスト設計書出力  │
                                                          └─────────────────┘
```

## Phase 1: Plan Reader（計画読込）

計画書を読み込み、テスト対象を特定する。

**実行内容:**
1. 計画書ファイルを読み込む
2. 実装ステップからテスト対象を抽出
3. 成功条件を確認

## Phase 2: Analyzer（リスク分析）

テスト観点からリスクを分析する。

**分析観点:**

| レイヤー | 分析内容 |
|----------|----------|
| Unit | 関数/クラス単位のロジック、境界値、エッジケース |
| Integration | モジュール間連携、API呼び出し、DB操作 |
| E2E | ユーザーシナリオ、画面遷移、エンドツーエンド |

**出力:**
```markdown
## リスク分析

### 高リスク（必須テスト）
- [機能/コンポーネント]: [リスク理由]

### 中リスク（推奨テスト）
- [機能/コンポーネント]: [リスク理由]

### 低リスク（任意テスト）
- [機能/コンポーネント]: [リスク理由]
```

## Phase 3: Designer（テスト設計）

各レイヤーのテストを設計する。

### Unit Test 設計

**設計観点:**
- 関数/メソッド単位の入出力
- 境界値（最小値、最大値、境界±1）
- 異常系（null、undefined、不正な型）
- エッジケース

**出力形式:**
```markdown
### Unit Test

#### [対象モジュール/関数名]
| テストケース | 入力 | 期待出力 | 優先度 |
|-------------|------|---------|--------|
| 正常系: [説明] | [入力値] | [期待値] | 高 |
| 境界値: [説明] | [入力値] | [期待値] | 高 |
| 異常系: [説明] | [入力値] | [エラー] | 中 |
```

### Integration Test 設計

**設計観点:**
- API エンドポイントのリクエスト/レスポンス
- データベース操作（CRUD）
- 外部サービス連携
- 認証/認可フロー

**出力形式:**
```markdown
### Integration Test

#### [対象API/モジュール]
| シナリオ | 前提条件 | 操作 | 期待結果 | 優先度 |
|---------|---------|------|---------|--------|
| [シナリオ名] | [前提] | [操作] | [期待] | 高 |
```

### E2E Test 設計

**設計観点:**
- ユーザーストーリーベースのシナリオ
- 主要な画面遷移
- クリティカルパス（ログイン、購入、登録など）

**出力形式:**
```markdown
### E2E Test

#### [ユーザーストーリー/機能名]
| シナリオ | ステップ | 期待結果 | 優先度 |
|---------|---------|---------|--------|
| [シナリオ名] | 1. [操作1]<br>2. [操作2] | [期待] | 高 |
```

## Phase 4: Review（外部レビュー）

別セッションでテスト設計をレビューさせる。

**レビュー依頼（両方に実行）:**
```bash
codex "/shin-reviewer $(cat ./docs/{topic}/qa-design.md)"
claude "/shin-reviewer $(cat ./docs/{topic}/qa-design.md)"
```
